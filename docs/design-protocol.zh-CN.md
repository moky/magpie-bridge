# Magpie Bridge 协议 — 设计

> Magpie Bridge（可靠的 UDP 中继网络）线上协议。
> 需求来源：`tasks/100-design-protocol.md`。

一个报文由**协议头**和可选**协议体**组成。接收方收到报文后必须逐个检查
协议头中的各个字段，不符合规范可直接丢弃。

## 1. 报文结构

```
+--------------------------------------------------------------+
| Head (20 octets fixed + optional parameter area)             |
+--------------------------------------------------------------+
| Body (0 .. N octets, N = 1200)                               |
+--------------------------------------------------------------+
```

## 2. 协议头（Head）

### 2.1 Magic Code（固定 4 字节）

`'M' (0x4D), 'B' (0x42), 0x00, 0x01` — 标识 Magpie Bridge v1。

### 2.2 测量校验区（固定 4 字节）

| 字段        | 宽度 | 含义                                          |
| ----------- | ---- | --------------------------------------------- |
| Type        | 1    | 包类型 + 参数宽度，见下                       |
| 协议头长度  | 1    | 报文头大小：20 / 22 / 24 / 28                 |
| 协议体长度  | 2    | 报文体大小；0 表示空体                        |

**Type** — 低位选择每个参数（`index`、`count`）的宽度；最高位（0x80）
标记应答包。四种规格：

| Type（数据包）| Type（应答包）| 参数宽度 | 消息大小 K            | 规格       |
| ------------- | ------------- | -------- | --------------------- | ---------- |
| 0x00          | 0x80          | 无       | 微型（单包）          | 微型数据包 |
| 0x01          | 0x81          | 1 字节   | 1 <= K < 256          | 一般数据包 |
| 0x02          | 0x82          | 2 字节   | 256 <= K < 65536      | 大文件     |
| 0x04          | 0x84          | 4 字节   | 65536 <= K < 2^32     | 超大文件   |

**协议头长度**可由 Type 推导，保留作为快速自检。

**协议体长度**必须满足 `头长度 + 体长度 <= MSS`。

### 2.3 Envelope（固定 12 字节）

| 字段             | 宽度 | 含义                         |
| ---------------- | ---- | ---------------------------- |
| Target Bridge ID | 4    | 目标 bid                     |
| Source Bridge ID | 4    | 源 bid（应答包回传至此）     |
| Serial Number    | 4    | 源端的消息身份标识           |

**序列号 sn** 按**原始数据包**（消息）自增，而不是针对单个包自增。
同一消息的拆分包 sn 相同；接收方用 sn 与 index 拼接来识别并去重
（消息, 分片）：

```
if type & 0x80 == 0:
    mid = sn
else:
    mid = (sn << (type & 0x0F)) | index
```

### 2.4 参数区（0 / 2 / 4 / 8 字节）

仅当 `Type != 0` 时存在：

```
+-----------------+-----------------+
| index (w octets)| count (w octets)|
+-----------------+-----------------+
```

- `count` — 分包总数（>= 1）。
- `index` — 当前分片编号，从 0 开始，`0 <= index < count`。
- 报文头大小随之确定：20（无参数）、22（w=1）、24（w=2）、28（w=4）。

## 3. 协议体（Body）

- 承载应用负载。
- 最大长度 `N = 1200`；允许空体（如纯应答包）。

## 4. 报文大小分析（MSS 与 N）

### 4.1 网络侧上限

为避免 IP 分片，每个发出的数据报必须小于任意路径都能保证的最小 MTU。
RFC 8200 规定 IPv6 最小链路 MTU 为 1280。

```
MSS = 1280 - 40 (IPv6 header) - 8 (UDP header) = 1232
```

1232 与 DNS Flag Day 2020 广泛部署的 EDNS(0) 建议一致。

### 4.2 报文体上限

报文头最大 28 字节（20 固定 + 8 参数区），理论最大体为 `1232 - 28 = 1204`。
协议预留 32 字节报文头预算：

```
N = MSS - 32 = 1200
```

### 4.3 评估 —— 维持 N = 1200

1. **与 QUIC 一致。** RFC 9000 强制初始数据报为 1200 字节（整个 UDP
   负载，含 QUIC 头）。该值已在 PPPoE（MTU 1492）、VPN 隧道（约 1400）、
   移动网络等公网路径大规模验证；1200 字节体加 28 字节头（共 1228）
   处于同一预算之内。
2. **留有余量。** `1228 <= 1232` 剩余 4 字节，可供未来头部扩展
   （如跳数字段）使用，无需改动 `N`。
3. **整数好记。** 1200 易于推理、测试与记录；相对理论值 1204 的损耗
   （0.3%）可忽略。

可选未来优化：Datagram PLPMTUD（RFC 8899）按目标地址提高上限（如纯
IPv4 以太网可到 1472）；`N` 保持为协议级安全默认值。
